# Email document language and direction — standards doctoring

Status: Implemented on active PR

## Decision under review

A self-contained HTML email document generated by Inkspan may preserve explicit document language and base writing direction on its root `<html>` element. Fragment output remains host-owned and therefore does not manufacture root-document metadata.

The product change is intentionally narrow: it does not change Markdown parsing, raw-HTML escaping, safe-link policy, inline-image policy, MIME construction, transport, persistence, recipient handling, or model authority.

## Normative and primary-source findings

### HTML language metadata

The WHATWG HTML Living Standard defines `lang` as the primary language of an element's contents and textual attributes. The value must be a valid BCP 47 language tag or the empty string. The standard also encourages authors to specify `lang` on the root `html` element to give the document language.

Product consequence: full-document generation is the point at which Inkspan owns the root element and can preserve a supplied language. Fragment generation cannot safely infer or own the outer document language.

### HTML base direction

The HTML `dir` global attribute defines element directionality and recognizes `ltr`, `rtl`, and `auto` as the known values relevant to this contract.

Product consequence: the TypeScript option is a closed literal union. Inkspan does not accept arbitrary direction strings and does not guess a direction when the option is absent.

### BCP 47

RFC 5646, together with RFC 4647, defines BCP 47 language-tag identification and matching. HTML points to BCP 47 for `lang` values.

Product consequence: Inkspan must never paste an arbitrary caller string into `lang`. The implementation uses ECMA-402's locale parser/canonicalizer as a conservative runtime validation boundary.

### ECMA-402 canonical locale processing

ECMA-402 13th edition (June 2026) defines `Intl.getCanonicalLocales()` through `CanonicalizeLocaleList`. Invalid locale identifiers produce an abrupt completion rather than a canonical result.

Product consequence: a non-blank language option is accepted only when the executing JavaScript runtime can canonicalize it through `Intl.getCanonicalLocales()`. This intentionally may reject a BCP 47 spelling outside the runtime's ECMA-402 canonical locale grammar even when a broader registry could recognize it. Fail-closed rejection is preferable to emitting unvalidated document metadata. The contract therefore does not claim exhaustive acceptance of every grandfathered or private-use BCP 47 tag in every runtime.

### WCAG 2.2 Language of Page technique

W3C WCAG Technique H57 describes using the `lang` attribute on the `html` element as a sufficient technique for identifying the page language, enabling user agents and assistive technologies to apply appropriate linguistic behavior such as pronunciation.

Product consequence: preserving known language metadata in full-document output removes an avoidable accessibility loss between authoring and deterministic email export. It does not by itself prove complete WCAG conformance for the host mail product.

## Alternatives considered

### Emit raw `languageTag`

Rejected. It would permit invalid metadata and would turn the root attribute into a markup-injection boundary unless independently escaped and validated.

### Hand-write a partial BCP 47 regular expression

Rejected. BCP 47 grammar, registered grandfathered values, extensions, and canonicalization rules are too broad for a small ad hoc regex to be a trustworthy standards implementation.

### Accept any BCP 47 registry-valid tag through a bundled registry parser

Deferred. It would broaden dependencies and maintenance scope for a feature whose main buyer need is preservation of ordinary application language tags such as `ko-KR` and `ar-SA`. The current runtime-canonicalizable subset is explicit and fail-closed.

### Infer language or direction from document text

Rejected. Deterministic export must not introduce a statistical/model inference step or claim knowledge the caller did not supply. `dir="auto"` is available when the caller deliberately wants user-agent direction resolution.

### Attach metadata to fragment output

Rejected. A fragment has no authoritative root element; the embedding host owns its surrounding language/direction context.

## Security and privacy review

- Raw authored Markdown remains behind the existing safe serializer.
- `languageTag` is canonicalized before root attribute emission and escaped defensively.
- `textDirection` is closed at the public TypeScript contract to `ltr | rtl | auto`.
- No network fetch, model call, environment read, credential, database, tenant identifier, recipient identifier, or durable audit claim is introduced.
- Invalid non-blank language metadata fails before a full document is returned.
- Fragment mode does not inspect or emit document-level metadata.

## Compatibility, rollback, and verification

The options are additive. Existing callers that do not supply metadata keep the previous output contract. Removing the options is a straightforward code rollback and does not reinterpret already generated or delivered HTML.

Verification requires known-answer Korean/Arabic cases, canonicalization, invalid-input rejection, blank omission, fragment/full-document separation, existing safe-link/image regression tests, repository-wide 100% owned production coverage, package/build/browser/Office/security/SAST evidence, and exact-head review before protected integration.
