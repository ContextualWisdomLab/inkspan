# ADR 0026: Bounded external hyperlinks in deterministic DOCX rich text

Status: Proposed

## Context

Inkspan Office already preserves bounded DOCX rich-text runs, paragraph/heading alignment, and informative inline PNG figures. Protected `main` does **not** yet expose a hyperlink target in `rich_paragraph.runs[]`; active PR #137 implements that additive fidelity surface. Without a public contract, hosts either flatten linked text to plain text or invent private OOXML outside Inkspan's deterministic renderer.

WordprocessingML represents a hyperlink with a `w:hyperlink` element whose `r:id` identifies a relationship carrying the target. ECMA-376 defines the Office Open XML vocabulary and package model, and Microsoft documents the `w:hyperlink r:id` relationship structure. `python-docx` 1.2.0 can read hyperlinks but still documents external hyperlink creation as not yet implemented, so Inkspan cannot rely on a stable public `Paragraph.add_hyperlink()` writer API.

The design must preserve Inkspan's network-free Office boundary while avoiding a second broad URL policy that silently expands the interactive editor's authority.

## Alternatives considered

1. **Continue flattening links to plain text.** Rejected because proposals, reports, references, and knowledge documents lose a common authored fidelity signal.
2. **Allow the complete interactive-editor link vocabulary.** Rejected because `mailto:`, telephone, relative, Unicode/IRI, protocol-relative, and other destination classes expand Office export policy without a demonstrated buyer requirement or cross-runtime normalization contract.
3. **Accept arbitrary URI strings and trust Word.** Rejected because local-file, executable/data, credential-bearing, whitespace/control-obfuscated, backslash, and ambiguous targets would become external package relationships outside Inkspan's fail-closed security model.
4. **Normalize or canonicalize internationalized/ambiguous targets inside Inkspan Office.** Rejected for this version because IDNA/IRI normalization, percent-encoding policy, and deceptive Unicode handling would create a new transformation authority and compatibility surface.
5. **Permit a deliberately narrower printable-ASCII absolute HTTP(S) subset and write the exact accepted target as one external hyperlink relationship.** Selected because it preserves the buyer-visible fidelity gap without adding network access, local-resource authority, or ambiguous normalization.

## Decision

An active `rich_paragraph.runs[]` item may optionally declare `href` under the following bounded contract:

- type: JSON string;
- length: 1 through 4,096 characters;
- character vocabulary: printable ASCII only;
- scheme: absolute `http` or `https` only;
- authority: non-empty hostname and syntactically valid optional port;
- embedded username/password: forbidden;
- backslashes, literal whitespace/control characters, relative/protocol-relative forms, local-file/UNC forms, unknown/executable/data/mail/telephone schemes, malformed authorities, and non-ASCII targets: rejected;
- accepted target: preserved byte-for-byte as the external relationship target; Inkspan does not fetch, resolve, probe, redirect, normalize, authorize, or inspect it.

The renderer creates the normal formatted Word run first, then moves that exact run beneath a `w:hyperlink` element. The `r:id` is generated by the package relationship layer and resolves to a relationship of hyperlink type with `TargetMode="External"`. The public JSON contract never exposes relationship IDs, arbitrary relationship types, raw OOXML, tooltips, target frames, bookmarks, fields, or tracked changes.

Visible run text remains fully Unicode-capable. The ASCII restriction applies only to the external target string. A host that needs an internationalized destination must supply an already authorized ASCII URI representation before calling Inkspan Office.

This ADR remains **Proposed** while #137 is an active PR. It becomes eligible for `Accepted` only after the unchanged implementation is integrated on protected `main` with the repository's applicable exact-head verification evidence.

## Consequences and ownership trade-offs

Inkspan preserves ordinary linked-text fidelity in deterministic DOCX output and exposes one small, reviewable security boundary. Existing requests remain source-compatible because `href` is optional.

The narrower URI vocabulary deliberately leaves some legitimate destinations to hosts. Hosts own business authorization, phishing/destination policy, allowlists, internationalized-URI conversion, tenant rules, distribution, and any link-health checking. Inkspan Office owns only structural validation and deterministic OOXML representation.

## Failure and recovery

Invalid `href` values fail during validation before artifact publication. Errors identify the structural field path but do not reflect the rejected target. `write_office_document()` retains its existing atomic/no-partial-publication behavior.

Recovery is explicit: correct or remove the invalid `href`, or have the host convert an authorized destination into the supported ASCII HTTP(S) representation before resubmission. Inkspan does not silently repair a rejected target.

## Security and privacy impact

The feature creates an external hyperlink relationship but performs **no external I/O**. It introduces no DNS, HTTP, redirect, browser, credential, filesystem-read, model, tenant, persistence, or authorization authority. Credential-bearing URLs and local/executable target classes fail closed. Non-ASCII targets fail closed to avoid introducing an unreviewed IDN/IRI/deceptive-Unicode normalization policy.

A syntactically accepted URL is not a safety or trust verdict. Hosts remain responsible for destination authorization and phishing/business policy. Ordinary validation diagnostics do not disclose rejected targets.

## Compatibility and migration

The schema change is additive for producers that omit `href`. Older Inkspan Office versions reject the new field because rich-run objects are strict; producers requiring hyperlink preservation must negotiate/target a renderer version that advertises this contract or omit the field.

No database, persisted schema, document-envelope, or host migration is introduced. If a future contract broadens URI support, it must specify normalization, cross-language parity, migration/compatibility, and security evidence explicitly rather than silently widening this decision.

## Verification and acceptance evidence

Active PR #137 is required to prove the boundary at the produced OOXML package, not merely through visible text:

- `w:hyperlink@r:id` resolves through `word/_rels/document.xml.rels`;
- relationship type is the external hyperlink relationship and `TargetMode` is `External`;
- relationship target exactly equals the accepted input;
- existing bold/italic/underline formatting and visible text are preserved;
- malformed, local, executable/data/mail/telephone, relative/protocol-relative, credential-bearing, whitespace/control/backslash, oversized, non-string, mapping/proxy-like, and non-ASCII targets fail closed without target reflection;
- repeated rendering of the same accepted request is byte-identical;
- Python 3.11–3.14 Office lanes retain 100% shipped production statement/branch coverage, 100% shipped-symbol docstrings, wheel/schema/license checks, and existing deterministic/atomic-publication behavior;
- repository CI, Security Scan, SAST, live-base compatibility, and applicable review/merge policy pass on the unchanged final head.

Historical failed heads are diagnostic evidence only and do not transfer acceptance to a changed head.

## Rollback or supersession

Rollback requires no data migration: producers can omit `href`, and the additive renderer/schema/test/docs changes can be reverted before a later release. Existing hyperlink-bearing artifacts remain ordinary OOXML documents but are not proof that the producing source still supports the contract.

Supersede this ADR if Inkspan intentionally broadens destination vocabulary, adopts a stable higher-level `python-docx` writer API with equivalent semantics, adds internal/bookmark links, or changes relationship/network authority. A successor must preserve explicit compatibility, failure, security, and migration behavior.
